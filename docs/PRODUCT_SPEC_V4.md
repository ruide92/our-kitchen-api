# 《我们家的大食堂 / 我们的小厨房》V4 产品规格

状态：Normative / Phase 2 Freeze

本文件定义产品行为。若旧交接文档、旧页面或旧 API 与本文件冲突，以本文件为准；数据字段以 `DATA_MODEL_V4.md` 为准，接口以 `API_CONTRACT_V4.md` 为准。

## 1. 产品定位

本产品不是传统菜谱工具，而是面向情侣与家庭的共享厨房系统。核心价值是把“今天吃什么、谁想吃什么、家里有什么、缺什么、怎么买、怎么做、做完以后库存和家庭反馈如何变化”连接为一条闭环。

核心闭环：

`家庭成员 → 周计划/随机推荐/手动选菜 → 本餐菜单 → 食材计算 → 冰箱/调味品抵扣 → 购物清单 → 买菜入冰箱 → 做饭 → 扣库存 → 评分/么么哒 → 历史 → 影响后续推荐`

## 2. 核心名词

以下概念不得混用：

- **公共基础菜谱 Base Recipe**：平台预置、所有家庭可浏览的基础做法，不允许家庭成员直接修改。
- **家庭菜谱 Family Recipe**：某个 `family_id` 私有的菜谱，可来自基础菜谱派生、AI 导入、手工新建或分享广场复制。
- **本周计划 Weekly Plan**：某家庭某周早/中/晚餐的计划安排。
- **本餐 Meal**：某个具体日期与餐次，例如 2026-09-03 晚餐。
- **本餐菜单 Meal Items**：该餐最终准备做的菜；记录谁点的。
- **冰箱库存 Fridge Inventory**：家庭实际拥有的食材库存。
- **常备调味品 Pantry Staples**：盐、生抽等长期存在、购物计算时可抵扣的家庭物品。
- **购物清单 Shopping List**：基于本餐菜单实际家庭菜谱、份量和库存计算出的缺失食材。
- **我想吃 Wish**：近期饮食意愿，不等同于收藏。
- **收藏 Favorite**：个人长期收藏。
- **评分 Rating**：个人对菜品/本餐完成结果的 1–5 星评价。
- **么么哒 Kiss**：家庭情感积分，不是价格、货币或评分。

## 3. 家庭与成员

### 3.1 家庭边界

所有共享业务数据都必须属于 `family_id`。同一家庭成员共享：

- 厨房名称和家庭照片
- 本周计划
- 本餐菜单
- 家庭菜谱
- 冰箱库存
- 常备调味品
- 购物清单
- 家庭设置
- 推荐历史
- 么么哒账本
- 家庭活动历史

不同家庭必须完全隔离。服务端必须通过已登录 `user_id` 校验其是否属于目标 `family_id`，不得只相信客户端传来的 family id。

### 3.2 成员角色

角色固定为：`OWNER | ADMIN | MEMBER`。

第一版权限：

- OWNER：管理家庭、成员、管理员与高风险设置。
- ADMIN：管理家庭菜谱、周计划、库存、购物及一般家庭设置。
- MEMBER：点菜、查看共享数据、使用购物清单、做饭、评分、收藏、么么哒互动。

### 3.3 邀请

家庭创建者可生成邀请码/分享邀请；已登录用户接受邀请后加入同一家庭。加入成功后加载家庭真实数据，而不是复制一份到本地。

数据模型保持 `users + families + family_members`，不使用 `users.family_id` 单字段锁死未来多家庭能力。

## 4. 登录与资料

身份流程：`wx.login → code → 服务端 code2Session → openid → user_id → 应用 Token`。

头像昵称属于资料完善，不属于身份主键。手机号不得成为核心使用前提。

## 5. 首页

首页视觉以用户确认的 UI 参考图为验收基准，业务行为以本规格为准。

### 5.1 顶部家庭区

- 左侧约 1/3：家庭/情侣合影，或双成员头像模式。
- 右侧约 2/3：可编辑厨房名称。
- 可显示轻量信息：星期、当前餐次、用餐人数。
- 所有内容来自家庭设置，不写死 `partnerAvatar` 等临时字段。

### 5.2 四个紧凑快捷入口

固定为高价值快捷动作，不做大面积卡片：

1. 随机菜谱 / 今天吃什么
2. 看冰箱做菜
3. 家人喜欢的菜（根据当前家庭成员自动命名，不永久写死“她”）
4. 一人菜

首页不增加资讯流、广告式模块或大型随机骰子区。

### 5.3 本周菜谱是首页核心

- 展示周一至周日。
- 默认突出今天。
- 今天区域展示早餐、午餐、晚餐及菜品缩略图/名称。
- 每餐可一键将计划中的菜加入对应本餐菜单。
- 提供“查看本周”进入完整周计划页。

### 5.4 已点菜单在首页下部

展示当前/最近餐次已经点好的菜，并显示点菜人，例如“糖糖点的”。可进入完整本餐菜单继续添加、删除或开始做饭。

## 6. 菜单 Tab

底部 Tab 固定五个：`首页 | 菜单 | 冰箱 | 购物清单 | 我的`。

菜单页内部分为：

- **本周安排**：管理周计划。
- **全部菜品**：浏览公共基础菜谱和家庭菜谱。

不得新增第六个 Tab 解决本餐菜单；本餐菜单通过悬浮条/页面进入。

## 7. 全部菜品

支持：分类、关键词、菜系、食材、厨具、快手菜、家庭常吃、最近吃过、我的菜谱、收藏。

分类至少覆盖：推荐、热菜、凉菜、汤羹、荤菜、素菜、主食、早餐、甜品。

选择菜品时支持加入当前餐次。页面底部在存在选中菜时显示类似：`今晚菜单 · 2 道  查看菜单`。

## 8. 菜品与家庭版本

### 8.1 基础菜谱

公共基础菜谱只读；作为公共默认资产。

### 8.2 “改成我家的做法”

用户点击后复制基础菜谱形成当前家庭私有 Family Recipe。之后该家庭在周计划、本餐菜单、购物、做饭流程中优先使用家庭版本。

家庭版本可编辑：

- 主料、配菜、调味、装饰料
- 数量、单位、是否必需
- 替代食材、备注
- 步骤、火力、时间、成熟判断、防失败提示
- 默认人数、厨具、口味属性、图片

支持查看原版、恢复原版；恢复不修改公共基础菜谱。

### 8.3 家庭共享

家庭菜谱属于 `family_id`，同一家庭成员看到同一版本；记录 `created_by` 与 `updated_by`。

## 9. 菜品详情

详情至少包含：

- 封面图、菜名、描述、菜系、分类
- 制作时间、难度、默认人数、厨具、烹饪方式
- 动态口味属性
- 营养参考与标签
- 么么哒建议值
- 主料/配菜/调味/装饰料
- 图文步骤
- 技巧、防失败、替代食材
- 库存状态
- 收藏、我想吃、加入菜单、改成我家的做法、开始做饭

### 9.1 动态口味

统一支持 0–5：`spiciness, sweetness, saltiness, sourness, oiliness`。UI 仅显示该菜有意义的维度，例如普通辣菜突出辣度，甜品突出甜度。

### 9.2 结构化食材

食材不得以一整块 textarea 作为正式存储。每项至少有：标准食材、展示名、数量、单位、类型、是否必需、替代食材、备注。

### 9.3 图文教程

每一步至少具有：序号、标题、操作、时间、火力、成熟判断、提示和 media。第一阶段允许没有步骤图，但接口和模型必须允许未来加入图片/AI 图片/视频关键帧。

### 9.4 份量缩放

按菜谱基准人数缩放可安全缩放的数量；购物计算必须使用本餐实际人数对应的数量。“少许/适量”等非精确值不强行数字化。

## 10. 营养

### 10.1 现代营养

长期目标根据当前配方动态估算每份热量、蛋白质、脂肪、碳水、膳食纤维、钠，并可扩展微量营养素。没有可靠数据库时只输出可信的结构化标签，不伪造精确数值。

UI 明示：“根据当前配方估算，仅供日常饮食参考。”

### 10.2 传统食养

若未来支持“温补/清热”等传统食养标签，必须与现代营养表分开，并标明文化/传统饮食参考，不做医疗功效宣称。

### 10.3 过敏与忌口

菜谱支持过敏原；成员设置的明确过敏原属于推荐硬约束。成员偏好、忌口、厨具都必须是数据，不硬编码“河南/湖南/不吃面食”等当前家庭背景。

## 11. 本周计划

### 11.1 默认数量

默认建议：

- 早餐 1–3 项
- 午餐 2–3 道
- 晚餐 2–3 道

是默认值，不是硬上限；允许增加第 4/5/6 道。主食可单独统计。

### 11.2 操作

支持：添加、删除、换一道、锁定、重新生成本餐、重新生成当天、重新生成整周。

锁定项重新生成时必须保留。

### 11.3 持久化与草稿

周计划生成后必须持久化。重新打开不能重新随机。重新生成先形成 draft/candidate，用户确认后再替换正式计划。

## 12. 推荐与随机点餐

周计划与“随机菜谱”必须共用同一推荐引擎，不允许一个是规则推荐、另一个是纯 `Math.random()`。

硬约束至少包括：过敏、明确忌口、当前餐次、可用菜谱。

软评分至少考虑：

- 蛋白来源与蔬菜多样性
- 烹饪方式多样性
- 家庭评分、收藏、我想吃
- 冰箱已有与快过期
- 常用厨具、制作时间
- 最近吃过的菜

默认重复惩罚：7 天强避开、14 天显著惩罚、28 天逐渐恢复；高评分常吃菜可减轻惩罚。细则见 `RECOMMENDATION_ENGINE.md`。

随机点餐至少三种模式：

- `BALANCED`：完全交给你
- `USE_INVENTORY`：优先吃库存/快过期
- `TRY_DIFFERENT`：换换口味、强排最近重复

结果提供“就吃这些”“再来一次”，支持锁定某道后重摇其余菜。

## 13. 本餐菜单与多人同步

本餐由日期、餐次、家庭唯一确定；菜品记录选择者。家庭成员添加/删除后其他成员通过重新进入、onShow 或下拉刷新获取最新状态。第一版不要求 WebSocket。

本餐菜单确认后是购物、做饭和扣库存的唯一上游，不直接用“本周计划”代替实际本餐菜单。

## 14. 冰箱与常备品

冰箱记录标准食材、数量、单位、储存位置、购买日期、到期日、备注；支持冷藏、冷冻、常温及扩展位置。

支持快过期/已过期提示，推荐系统提高快过期食材相关菜谱权重。

常备调味品独立管理，购物算法真实抵扣，不得仅在 UI 声称“已有”。

## 15. 标准食材与购物

建立 canonical ingredient + aliases，例如“番茄/西红柿”归一。安全单位转换由数据模型明确；“个/根/瓣/勺/适量”无可靠换算时不瞎转克。

购物算法：

`本餐菜单 → 家庭版本 → 份量缩放 → canonical 归一 → 单位归一 → 同类合并 → 减冰箱 → 减常备品 → 缺失数量 → 购物清单`

详情页可显示“需要/已有/缺少”；若用户发现家里其实有，可直接补录冰箱并重新计算。

购物勾选状态必须服务端共享。购买完成后勾选项一键进入冰箱；相同标准食材与兼容单位应累加而不是重复成两行。

## 16. 做饭与扣库存

流程：开始做饭 → 查看结构化步骤/做饭模式 → 完成 → 显示预计消耗 → 用户确认或调整 → 扣库存。

打开菜谱不得扣库存。未来做饭大字模式支持一步一屏、计时、火力与成熟判断。

## 17. 收藏、评分、我想吃

- Favorite：个人长期收藏。
- Rating：个人 1–5 星，可取消；家庭喜爱度可计算家庭成员评分平均。
- Wish：近期“我想吃”，用于近期推荐权重，不与收藏合并。

## 18. 么么哒

么么哒是家庭情感积分，不是钱、支付或普通评分。菜谱上的 `suggested_kiss` 只是建议值，实际赠送写入独立账本。

记录：谁赠送、谁获得、哪个家庭、哪一餐、哪道菜、建议值、实际值、评分、原因、时间。

第一阶段用于月度/累计情感记录；未来可由家庭自定义奖励规则。禁止充值、现金兑换或平台货币化。

## 19. AI 菜谱导入

使用 KRP v2。流程：外部链接/截图/文字/视频信息 → 支持的 AI + Recipe Skill → KRP → 小程序粘贴 → 解析 → schema 校验 → 缺失/推断提示 → 预览 → 用户修改 → 确认 → Family Recipe。

不得粘贴后无校验直接入库。AI 合理补全必须标 `inferred_fields`，不得伪称原作者明确给出。

图文教程、封面图提示词、步骤图提示词等结构见 `KRP_V2_SPEC.md`。

## 20. 分享广场

核心厨房稳定前只冻结数据边界和入口，不实现完整社区。

Family Recipe 默认 `FAMILY` 或 `PRIVATE`；用户主动发布才成为 `PUBLIC`。其他家庭“加入我家菜谱”时复制形成自己的 Family Recipe，不获得修改发布者原菜谱的权限，并记录来源/Fork 关系。

后续社区功能（推荐流、评论、关注、举报、审核等）不属于当前 P0。

## 21. 我的 / 设置

“我的”至少保留入口：家庭管理、厨房设置、本餐菜单/历史、收藏、评分、我的菜谱、AI 导入、调味品、么么哒、分享广场、我的分享、回收站、设置；低优先级入口可阶段性显示“规划中”，但不能误报已实现。

厨房设置至少包含：厨房名称、家庭合影/头像模式、成员、默认人数、各餐默认菜数、口味、辣度、忌口、过敏原、不喜欢食材、常用厨具、常备品、推荐偏好、重复周期、随机偏好。

## 22. 原始扩展能力

以下保留 Roadmap，不抢占核心闭环：一人菜增强、宝宝辅食、老人餐、多厨房切换、操作日志 UI、数据导入导出、AI 图片、完整分享广场。

“一人菜”当前至少是一个推荐 profile：份量小、耗时短、少剩菜。

## 23. UI 与交互基准

- 原生微信小程序，真实手机比例，主要参考 iPhone 14/15。
- 温暖、清爽、有生活感；暖米白背景、绿色主操作、粉色情感提示、紧凑圆角卡片。
- 首页菜单优先；随机只是快捷入口。
- 普通操作直接执行并给反馈；危险操作才二次确认。
- 已确认的 UI 参考图是 UI Acceptance Reference；如必须偏离，记录 `docs/UI_DEVIATIONS.md`。

## 24. 完成定义

页面存在不等于完成，API 200 不等于完成。一个功能只有在对应验收测试通过、家庭边界正确、重载后数据保持且无假接口时才能标记 DONE。
