# V4 推荐引擎规范

状态：Normative / Phase 2 Freeze

本文件定义“每周菜谱、随机点餐、看冰箱做菜、一人菜”共用的一套推荐基础。禁止分别开发互不一致的三套随机算法。

## 1. 目标

推荐不是医疗营养处方，而是家庭日常饮食的规则化、可解释建议。目标优先级：

1. 不违反硬性过敏/忌口。
2. 餐次与家庭人数适配。
3. 荤素、蛋白来源、蔬菜与烹饪方式不过度单一。
4. 减少近期机械重复。
5. 结合家庭喜好、库存和快过期食材。
6. 保留一定随机性，避免每次结果完全相同。
7. 给出可解释原因，而不是黑盒分数。

## 2. 输入

推荐上下文至少包含：

- `family_id`
- `meal_date`
- `meal_type`
- `diners_count`
- `mode`：`BALANCED | USE_INVENTORY | TRY_DIFFERENT`
- `target_count`
- `locked_recipe_ids`
- family settings
- ACTIVE family members + preferences
- available BASE/FAMILY recipes
- family recipe overrides
- ratings/favorites/wishes
- meal history
- fridge inventory + expiry
- pantry staples
- cookware

## 3. 有效菜谱选择

若某 BASE recipe 在当前家庭存在未删除的家庭派生版，推荐候选应优先使用 FAMILY variant；同一基础菜逻辑族不要把 BASE 和该家庭 variant 同时当两个独立候选增加重复概率。

家庭手工/KRP/社区 Fork 菜谱直接作为 FAMILY candidate。

## 4. 硬过滤

任何 candidate 先经过硬过滤，不通过则绝不能仅靠高分进入结果。

硬过滤：

1. 已删除/隐藏或当前家庭无权访问。
2. 明确过敏原与当前用餐成员冲突。
3. 明确禁用/忌口标签冲突。
4. meal_type 明确不适配且没有通用餐次标签。
5. recipe 缺少最基本可执行数据（例如无名称/无食材，除非产品阶段明确允许占位）。
6. 用户请求限定厨具且菜谱必须依赖家庭完全没有的专用厨具时，可过滤；普通“常用厨具偏好”只做软分。

普通“不喜欢”不等于过敏，默认做高惩罚而不是硬删除；家庭设置允许以后升级为 hard exclusion。

## 5. 餐次组合模板

模板只用于保证组合不荒谬，不是绝对饮食医学规则。

### 早餐

目标 1–3 项。槽位示例：

- 主食/谷物/简单碳水 0–1
- 蛋/奶/豆/肉类蛋白 0–1
- 水果/蔬菜/粥汤等 0–1

### 午餐

默认 2–3 道：

- 主要蛋白菜 1
- 蔬菜类 1
- 可选汤/第二蔬菜/豆制品 0–1

### 晚餐

默认 2–3 道：

- 主要蛋白菜 1
- 蔬菜类 1
- 可选汤/清淡配菜 0–1

用户设置的 target_count 优先于默认；4–6 道时扩展槽位而非复制相同类型。

主食可以独立于 dish target count。

## 6. 组合约束

生成一餐时至少避免：

- 所有菜都是纯肉/高油重口。
- 所有菜主要蛋白来源完全相同，除非候选库不足。
- 三道菜全部同一种强烹饪方式（如全油炸/全爆炒）。
- 明显重复菜谱族同时出现（例如公共番茄炒蛋 + 家庭番茄炒蛋）。

当候选库不足无法满足时，允许降级，但必须在 response `reasons/warnings` 说明。

## 7. 单菜基础评分

先归一为 0–100 的内部 score。默认权重只是初始值，后续可调参但改动需测试。

建议初始组成：

- 家庭喜好/评分：0–20
- 收藏/我想吃：0–12
- 库存匹配：0–18
- 快过期利用：0–12
- 餐次适配：0–10
- 厨具/时间适配：0–8
- 多样性潜力：0–10
- 随机扰动：0–10

然后减去：

- 最近重复惩罚：0–40+
- 不喜欢食材惩罚：0–35
- 与当前 locked/已选组合重复的蛋白/烹饪方式惩罚：0–15

硬约束从不通过“负很多分”实现，而是在评分前过滤。

## 8. 家庭喜好

示例计算：

- 家庭平均 rating 5★：+20
- 4★：+14
- 3★：+5
- 2★：-6
- 1★：-15
- 无评分：0

收藏可 +4/人，上限 +8。

ACTIVE wish 可 +8，若多个家庭成员都 wish 可再 +2，但总项不超过 12。

没有足够历史时保持中性，不要给新菜负分。

## 9. 最近重复

以真实 `COMPLETED` meal history 为主要依据，`CONFIRMED/COOKING` 可视为即将食用并参与短期惩罚。

默认：

- 距离上次 ≤7 天：强惩罚，例如 -40。
- 8–14 天：显著惩罚，例如线性 -25 → -15。
- 15–28 天：逐渐恢复，例如 -12 → 0。
- >28 天：0。

对应天数读取 `family_settings.repeat_*_days`。

高评分/家庭常吃可最多抵消一部分重复惩罚，但 7 天内默认仍保留明显惩罚，避免“喜欢辣椒炒肉”导致天天辣椒炒肉。

`TRY_DIFFERENT` 模式将重复惩罚乘 1.5–2.0，并提高菜系/蛋白/烹饪方式新颖度权重。

## 10. 库存匹配

对 recipe 按标准 ingredient + 可换算单位估算：

- 必需主料全部/大部分已有：高加分。
- 多数配菜已有：中加分。
- 只有盐/调味品已有：不能声称“家里就能做”。

库存匹配建议根据“必需食材满足比例”和“需购买成本代理（缺失项目数/比例）”计算，而不是只看名字命中数。

`USE_INVENTORY` 模式库存权重提高约 1.5 倍。

## 11. 快过期

对 `expiry_date`：

- 已过期：不作为可用库存；UI 应提示处理。
- 0–1 天到期：最高优先利用分。
- 2–3 天：高。
- 4–7 天：轻度。
- >7 天：不特别加分。

只有菜谱真实需要该 ingredient 且能消耗有意义数量时加分；盐等常备调料不参与“快过期推荐”。

`USE_INVENTORY` 模式快过期权重提高。

## 12. 时间与厨具

家庭拥有所需厨具：正常/加分。

家庭没有普通可替代厨具：轻惩罚或给替代建议。

家庭完全没有不可替代专用厨具：可硬过滤。

若未来用户选择“30 分钟内”，则 `cook_time_minutes` 作为硬/强约束；默认仅作为轻度适配。

## 13. 多样性评分

一餐选菜采用逐步构造，而不是每道独立 top-N 后直接拼接。

步骤：

1. 按槽位选第一道主要菜。
2. 第二道对“与已选菜组合”重新计算 marginal score。
3. 第三道再次根据当前组合重算。

marginal diversity 加分：

- 新蛋白来源
- 新蔬菜类别
- 不同烹饪方式
- 重口 + 清淡互补

惩罚：

- 相同 protein_source 重复
- 全部 STIR_FRY
- 全部高 oiliness/spiciness

## 14. 随机性

推荐不能固定 top 1 每次相同，也不能纯随机。

建议：过滤后按 score 转概率，使用 softmax/加权抽样；仅在高质量候选池（如 top 20% 或达到阈值）中随机。

随机 seed 可由 request_id 生成；测试环境支持固定 seed 以保证可复现。

同一按钮连续“再来一次”可把上一轮候选加入短期 session penalty，避免立刻原样返回。

## 15. 锁定

`locked_recipe_ids`：

- 首先验证仍可访问且不违反硬约束。
- 锁定项固定进入结果并占用目标槽位。
- 其余菜根据与 locked 的组合多样性重新推荐。
- target_count 小于锁定数量时返回 422，不自动删除锁定项。

周计划 regenerate 同理使用 `weekly_plan_items.locked=true`。

## 16. 周计划生成

周计划不是独立算法，而是把每日三餐推荐放入一周全局上下文：

- 每生成一餐，把 candidate 先加入“计划内近期历史”，后续餐次计算重复/蛋白/烹饪方式时考虑已生成结果。
- 不要求一周每天都完全不同，但避免同一道菜机械重复。
- 营养主题可以作为 explain label，例如“鱼类蛋白 + 绿叶菜”，不能用固定文案冒充实际分析。

生成结果先写 DRAFT；用户确认后 ACTIVE。

## 17. “看冰箱做菜”

该功能共用 scoring，但 UI 可按三个等级展示：

- `CAN_COOK_NOW`：必需食材在库存/常备品中基本满足。
- `MISSING_FEW`：缺少少量食材，例如 1–2 类。
- `NEEDS_SHOPPING`：缺失较多。

状态必须来自标准食材和单位计算，不用简单字符串包含。

## 18. “一人菜” profile

当 diners_count=1 或用户主动选择一人菜：

提高：

- cook_time 短
- ingredient count 少
- 可按 1 人缩放
- 单锅/简单厨具
- 剩菜风险低

降低复杂大份炖菜等权重，但不必全部硬过滤。

## 19. 可解释输出

推荐 API 对每个 candidate/整餐至少可返回用户友好的 reason codes：

- `FAMILY_FAVORITE`
- `WISH_MATCH`
- `USE_EXPIRING_INGREDIENT`
- `HIGH_INVENTORY_MATCH`
- `PROTEIN_VARIETY`
- `VEGETABLE_BALANCE`
- `COOKING_METHOD_VARIETY`
- `TRY_SOMETHING_DIFFERENT`
- `QUICK_TO_COOK`

UI 可翻译为：

“冰箱里的苦瓜明天到期，优先帮你安排了苦瓜炒蛋。”

禁止返回伪医学结论。

## 20. 降级策略

当数据不足：

- 无历史：忽略 repeat/ratings，使用基础多样性和少量随机。
- 无库存：库存项中性，不判定“家里没有所以不能做”。
- 菜谱结构标签不足：不要硬编 protein/vegetable；进入数据质量 warning。
- 候选不足：放宽软约束，绝不放宽过敏硬约束。

## 21. 测试要求

必须有确定性测试 seed，覆盖：

1. 过敏菜永不进入结果。
2. 7 天内重复显著受罚。
3. 锁定菜不被替换。
4. USE_INVENTORY 提高快过期食材菜谱选择率。
5. TRY_DIFFERENT 比 BALANCED 更少近期重复。
6. 三道结果不机械成为同蛋白+同烹饪方式。
7. 相同输入+固定 seed 结果可复现。
8. 无历史/无库存仍可正常推荐。

验收不要只断言“返回 3 道”；还要验证规则真实生效。
